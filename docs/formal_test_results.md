# 正式 Test 评估记录

## 1. 评估范围与固定方案

本项目评估单轮工具选择、参数生成，以及澄清和不支持操作的判断。
输出采用自定义 JSON 协议，不连接业务数据库、不执行真实工具。

Test 共 200 条请求：120 条 call、60 条 clarify、20 条 unsupported。
全部采用明确撤回旧请求、再提出当前请求的单轮表达结构。

比较方案：

- baseline：Qwen3-8B 4-bit 量化基座，无 LoRA adapter。
- step450：通过正式 Validation 选择，并在 Test 前锁定的 LoRA checkpoint。

模型仓库：`mlx-community/Qwen3-8B-4bit`。

模型 revision：`545dc4251c05440727734bcd94334791f6ab0192`。

候选权重：

`adapters/formal/run_20261017T014551_717380Z/0000450_adapters.safetensors`

两组使用相同的 Test 数据、系统提示词和工具定义。
生成设置均为关闭 thinking、temperature=0、max_tokens=256。

## 2. 评估口径

主指标为全部自动检查通过率，要求：

1. 原始输出能够严格解析为 JSON 对象。
2. 输出满足动作结构与工具接口约束。
3. action 与参考答案一致。
4. 参考答案为 call 时，工具名称和全部参数完整匹配。

参考答案为 clarify 或 unsupported 时，另外审查说明文字。

合并通过要求：调用请求完整正确；非调用请求同时通过自动检查与说明审查。
整体分母始终为 200，自动失败样本不会被排除。

## 5. 配对比较与观察

按同一请求的合并判定比较：

- 两组均通过：122 条。
- 两组均失败：31 条。
- step450 改善：10 条。
- step450 退化：37 条。

37 条新增退化均来自参考答案为 call 的请求：
销售统计 19 条、物流查询 9 条、商品信息查询 7 条、库存查询 2 条。

step450 的合格非调用说明增加 10 条，但正确调用减少 37 条，
因此整体净减少 27 条。

### 5.1 新增退化的错误类型

逐条核查这 37 条请求和两组保存输出后发现：
baseline 均生成正确调用，step450 均输出 clarify，
重复要求用户提供或确认输入中已有的信息。

| 请求类型 | 重复追问的信息 | 数量 |
| --- | --- | ---: |
| 库存查询 | 商品编号 | 2 |
| 商品信息查询 | 商品编号 | 7 |
| 物流查询 | 订单编号 | 9 |
| 销售统计 | 起始日期和结束日期 | 12 |
| 销售统计 | 统计指标 | 7 |
| 合计 | — | 37 |

这 37 个 step450 输出均通过 JSON 对象和接口检查，
但 action 与当前请求不匹配。
错误类型为信息齐全时的不必要澄清，而非输出格式错误。

### 5.2 代表性库存查询案例

样本编号：

`formal_test_correction_inventory_001__formal_test_params_020`

用户输入：

> 请查商品 P12120 的名称和规格。更正：撤回上一句查询要求，本次只查这件商品的当前库存数量。

baseline 正确生成 get_inventory 调用，product_id 为 P12120。

step450 输出 clarify，说明为：

> 请提供要查询库存数量的商品编号。

用户撤回的是查询名称和规格的任务。
“这件商品”仍明确指向 P12120，因此当前库存查询不缺少商品编号，
无需再次要求用户提供。

本案例体现了同一条输入中，任务发生更正时对已有参数和指代信息的利用问题。

### 5.3 共同失败与参数改写案例

两组模型在 31 条请求上的合并判定均失败，按请求模板分类如下：

| 请求类型 | 数量 |
| --- | ---: |
| 查询已有退款申请状态 | 17 |
| 修改订单收货地址 | 3 |
| 无效日历日期 | 4 |
| 同时统计多项销售指标 | 1 |
| 小数库存阈值 | 3 |
| 创建退款申请 | 3 |
| 合计 | 31 |

共同失败只表示两组在同一请求上均未通过，
不意味着两组输出或具体错误完全相同。

其中一个参数改写案例的样本编号为：

`formal_test_correction_low_stock_fractional_threshold_001__formal_test_params_007`

用户输入：

> 请查商品 P12107 的当前库存数量。更正：撤回上一句查询要求，本次只列出库存数量严格小于 6.5 件的商品。

两组均输出 call，调用 list_low_stock_products，
并将 threshold 设置为整数 6。

该输出满足工具接口的正整数约束，但擅自改变了用户提供的阈值。
例如，假设某商品库存为 6，它满足“严格小于 6.5”，
却不满足“严格小于 6”，查询结果可能因此改变。

按照当前协议，小数阈值不符合接口要求，应输出 clarify，
请用户确认要使用的正整数阈值，不能自行取整后调用工具。

本案例属于两组共同失败，不属于 step450 的 37 条新增退化。
它说明接口结构合法与用户意图匹配需要分别检查。

### 5.4 改善样本分析

step450 在 10 条请求上的合并判定由失败变为通过：

| 请求类型 | 说明改善的具体表现 | 数量 |
| --- | --- | ---: |
| 不支持的商品分类 | 明确列出支持的分类并要求用户确认 | 2 |
| 负数库存阈值 | 准确解释阈值约束，避免引入库存不能为负的业务规则 | 5 |
| 零库存阈值 | 正确说明正整数阈值要求，区分阈值约束与实际库存 | 2 |
| 同时统计多项销售指标 | 要求在当前有效的两项指标之间选择，不再引入已撤回的退款查询 | 1 |
| 合计 | — | 10 |

这 10 条请求中，两组均输出 clarify，且均通过自动检查。
按既定说明审查标准，baseline 的说明均为 needs_improvement，
step450 的说明均为 pass。

因此，这 10 条改善来自澄清说明的语义质量。
该判断属于导师指导的非盲审，结论限于当前样本与审查标准。

### 5.5 解释边界

正式 Validation 的合并通过率由 86.0% 提高至 90.5%，
这一提升没有在当前 Test 上保持。

上述分析确认了新增退化的具体表现：
在当前更正表达结构下，对已有信息进行不必要的澄清。
这些输出尚不足以确定具体训练机制或退化原因。

按冻结方案保留本次结果，不依据 Test 继续选择 checkpoint 或调整参数。
